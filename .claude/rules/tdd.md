# TDD Rule

**이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸거나 "이번만 예외"를 만들지 않는다.

## 우선순위

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선한다.**
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙과 충돌하는 부분은 프로젝트 규칙을 따른다.

## 적용 기준

### TDD 필수

- 비즈니스 로직
- API (핸들러, 요청/응답 처리, 에러 매핑)
- 유틸 / 순수 함수
- **버그 수정** (버그를 재현하는 실패 테스트를 먼저 작성)

### TDD 불필요

- 타입 정의
- 설정 파일
- 순수 UI (로직 없는 마크업/스타일)
- SQL

경계가 모호하면 **적용 대상으로 간주한다.**

## RED - GREEN - REFACTOR

### RED

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 않는다.
- 테스트를 작성하면 **반드시 실행해서 실패를 확인한다.** 실행하지 않은 RED는 RED가 아니다.
- 실패 이유는 **"기능 미구현"** 이어야 한다. 오타, import 오류, 문법 오류로 인한 실패는 RED가 아니므로 먼저 고친다.
- 처음부터 통과하는 테스트는 아무것도 증명하지 못한다. 테스트를 수정한다.

### GREEN

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI.** 지금 테스트가 요구하지 않는 기능, 분기, 옵션을 추가하지 않는다.
- **신규 테스트와 기존 테스트 모두** 실행해서 통과를 확인한다.

### REFACTOR

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **green 상태를 유지한다.** 리팩터링 후 전체 테스트를 다시 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작은 다음 RED에서 시작한다.

### 반복

다음 동작이 남아 있으면 **RED로 돌아간다.** 한 번에 여러 동작을 구현하지 않는다.

## 삭제 강제

테스트보다 프로덕션 코드를 먼저 작성했다면:

1. **그 코드를 삭제한다.**
2. RED부터 다시 시작한다.

- "참고용"으로 남기거나, 주석 처리하거나, 옆에 두고 보면서 다시 쓰는 것도 **금지**다.
- 삭제한 코드를 복원하지 말고 테스트가 요구하는 대로 새로 작성한다.

## 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순한 코드가 가장 많이 깨진다. 테스트도 단순하니 작성 비용은 거의 없다. |
| "나중에 테스트 추가하겠다" | 나중에 쓴 테스트는 구현에 맞춰지고 즉시 통과한다. 아무것도 검증하지 못한다. |
| "시간이 없다" | 디버깅과 회귀 수정이 테스트 작성보다 오래 걸린다. 급할수록 TDD가 빠르다. |
| "삭제하면 낭비다" | 매몰 비용이다. 검증되지 않은 코드를 유지하는 것이 더 큰 비용이다. |
| "프로토타입이다" | 프로토타입은 프로덕션이 된다. 버릴 코드라면 어차피 삭제 비용도 없다. |
