# commit: 변경사항 분석 후 컨벤션 커밋

## 원칙

- 커밋은 사용자 승인을 따로 받지 않고 바로 진행한다. 커밋 후 파일 목록과 메시지를 보고한다.
- `git add -A`, `git add .`는 쓰지 않는다. 커밋 단위별로 파일을 명시해서 스테이징한다.
- `.env`, 키·토큰이 들어간 파일, `node_modules`, `dist` 등은 커밋 대상에서 제외하고, 발견하면 사용자에게 알린다.
- hook 실패 시 `--no-verify`로 우회하지 않는다. 원인을 고쳐서 새 커밋을 만든다.
- 푸시는 하지 않는다. 사용자가 요청할 때만 한다.

## 절차

### 1. 변경사항 분석

```bash
git status --short
git diff            # 스테이징 안 된 변경
git diff --staged   # 이미 스테이징된 변경
git log --oneline -10   # 기존 메시지 스타일 확인
```

- 변경이 없으면 "커밋할 변경사항이 없습니다."라고 알리고 끝낸다.
- 새로 추가된(untracked) 파일은 내용을 읽어 목적을 파악한다.
- git 저장소가 아니면 그 사실을 알리고 중단한다.

### 2. 논리적 단위로 분류

- 하나의 커밋은 하나의 목적만 담는다. 기능 추가, 버그 수정, 리팩터링, 설정 변경이 섞여 있으면 나눈다.
- 같은 기능의 코드, 테스트, 스타일은 한 커밋으로 묶는다.
- 한 파일 안에 서로 다른 목적의 변경이 섞여 있어도 묻지 않고, 파일 단위로 가장 가까운 커밋에 넣은 뒤 보고에 그 사실을 적는다.
- 분류 결과를 "커밋 1: 파일 목록, 이유" 형태로 정리한다.

### 3. 한국어 커밋 메시지 작성

형식:

```
<type>: <요약>

<본문 (선택)>
```

| type | 용도 |
| --- | --- |
| feat | 사용자에게 보이는 기능 추가·변경 |
| fix | 버그 수정 |
| refactor | 동작 변화 없는 구조 개선 |
| chore | 빌드, 의존성, 설정, 기타 잡무 |

- 요약은 50자 안팎, 한국어, 마침표 없이 명사형 또는 `~한다`로 끝낸다. 하나의 커밋 안에서 통일한다.
- 무엇을 했는지보다 **왜** 했는지가 드러나게 쓴다. 이유가 diff만으로 분명하지 않으면 본문에 1~3줄로 적는다.
- 기존 `git log` 스타일이 있으면 그것을 따른다.
- 위 4개 외 type(docs, style, test 등)이 필요해 보이면 가장 가까운 것을 쓴다.

### 4. 바로 커밋

1. 승인을 기다리지 않고 커밋 단위마다 파일을 명시해 스테이징하고 커밋한다. 메시지는 HEREDOC으로 넘긴다.

   ```bash
   git add <파일들>
   git commit -m "$(cat <<'EOF'
   feat: 요약

   본문
   EOF
   )"
   ```

2. 대화 컨텍스트에 커밋 attribution 지침(Co-Authored-By 등)이 있으면 메시지 끝에 그대로 붙인다.
3. 모든 커밋이 끝나면 `git log --oneline -N`과 `git status --short`로 결과를 확인하고, 커밋별 파일 목록과 메시지를 보고한다.
4. 사용자가 메시지나 분류를 고치고 싶어 하면 `git commit --amend` 또는 `git reset --soft`로 정리하기 전에 어떤 방식으로 고칠지 알리고 진행한다.
